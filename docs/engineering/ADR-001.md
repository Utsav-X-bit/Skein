# ADR-001 — Collapse to one privileged daemon + minimal helper

- **Status:** Decided and approved by the user, 2026-11-04. Implemented on
  branch `collapse/adr-001` (base `f6bc79b`, "CheckPoint-1"), uncommitted,
  for review — not on upstream `main`.
- **Supersedes:** the pre-collapse three-actor layout (`skein` doing daemon +
  service + client work, `skeind` as a thin wrapper, and a wide
  `skein-helper` performing init/join/import, rotation, resets, and updates
  with elevation).

## Decision

One privileged actor: the daemon/service (`skeind`). It owns the TUN device,
routes, firewall, sessions, peers, and config — config as the single writer
via `internal/configstore` under a cross-process lock beside the config file
(`<config>.lock`) — and serves the control API, including init/join/import,
rotate-secret, reset, leave, update check/apply, and grants reload. The GUI
stays unprivileged always; the CLI is a control-API client (plus the dev-only
`skein run` path) and never writes system config directly or spawns a daemon.

The minimal helper (`skein-helper`, elevated via pkexec/UAC/polkit) retains
only:

| Verb | Does |
|---|---|
| `bootstrap --verb init\|join\|import` | Mints one single-use token, installs + starts the daemon into bootstrap mode |
| `install [--daemon <path>]` | `RegisterDaemon` (package `skeind` only, or an explicit validated path) + start |
| `uninstall [--purge]` | Stop-then-delete; config purge itself is the daemon reset endpoint |
| `start`, `stop`, `restart` | Service lifecycle (`restart` retained: no daemon restart endpoint exists) |
| `status` | Unprivileged, no polkit action |
| `grant-user <uid> [--role]` (Linux) / `set-owner` (Windows) | Access grants |
| `revoke-user <uid-or-user> [--force]` | Removes a grant + daemon grants-reload |

Removed helper verbs return exit 1 with the daemon endpoint that replaces
them: `init`, `join`, `import` → `skein-helper bootstrap --verb …` then
`POST /api/v1/bootstrap/…`; `rotate-secret` →
`POST /api/v1/system/rotate-secret`; `reset` →
`POST /api/v1/system/reset` then helper `stop`; `update-daemon` →
`GET /api/v1/system/update/check` then `POST /api/v1/system/update/apply`.

## Bootstrap mechanism (approved 2026-11-04)

The one new security mechanism in the collapse. First configuration cannot
go through the normal role-gated API (no config, identity, or grant exists
yet), and pkexec/UAC elevation is the proof the user approved the step:

1. The helper checks that no system config exists under a brief lock,
   generates 256 bits with `crypto/rand`, and stores only the SHA-256 hash
   (root-owned 0600 state file, with the invoking uid/SID, a 10-minute
   expiry, and the verb it was minted for). It installs and starts the
   daemon and returns the plaintext token once in stdout JSON to the
   invoking GUI/CLI — held in memory only, never logged, never written to
   disk in plaintext.
2. The daemon starts in bootstrap mode: control socket/pipe only — no TUN,
   no UDP port, no mDNS, no firewall, not a mesh member. It accepts exactly
   one `POST /api/v1/bootstrap/init|join|import` with the token in the JSON
   body, verified in order: kernel transport (bearer/dev-TCP callers get 403
   even with a valid token), uid/SID match, constant-time hash match,
   expiry, unused. Five failed attempts burn the token.
3. On success the token is marked used atomically before any config work,
   the daemon writes config and identity as sole writer, grants the
   bootstrap caller the `secret` role, deletes the state file, and switches
   in-process to normal mode.

Fallback if review rejects the token: a pending-request file the daemon
consumes instead. Explicitly rejected: unauthenticated bootstrap from any
local uid, long-lived bootstrap passwords, plaintext tokens on disk, and
bearer-token bootstrap over a dev TCP port.

## Prerequisites, in order (all implemented in this branch)

1. IPC authorisation — `read` / `mutate` / `secret` / `bootstrap` roles,
   endpoint × role × transport matrix test written test-first. Legacy bare
   uid/SID access lines map to `read`, not `mutate`.
2. Single control listener (`StartControlListeners`), fatal on bind failure
   — the daemon never runs headless with a dead control plane — plus daemon
   server-identity verification on every dial path (`VerifyPipeServer`,
   Unix check).
3. Single config writer + cross-process lock (`internal/configstore`).
4. Service binary identity fixed — service always registers the daemon
   binary (`RegisterDaemon`, `skeind` only); upgrades adopt the new binary
   without rewriting the unit, keeping `<binary>.old` + timestamped config
   backups, never deleted on failure.
5. Daemon system endpoints + self-update: signed manifest (ed25519 +
   SHA-256, `key_id` + signed `valid_until`, basename-only binary under the
   staging directory), downgrade protection (new version strictly greater),
   detached apply process with verified rollback.

## Companion decision: equal peers (ADR-002)

Every peer is equal; any peer can act as a relay (capability-based
selection by measured reachability, address-family coverage, RTT/loss/
stability — not a role), and relaying stays opaque (a relay never holds the
pair's session keys). Anyone can invite. No peer removes another peer: a
peer leaves itself and gossips a version 5 tombstone so all peers update
their tables and routes (see `docs/protocol.md`, STATE v5). Leave is
graceful departure, not a ban — the leaver keeps its credential until a
network-wide secret rotation, and rejoining needs a fresh invite. Rotation
evicts only after the service restarts and every legitimate node rejoins
with the new secret.

## Migration and rollback

The daemon adopts existing system config and identity unchanged (no silent
conversion, no silent rotation). The one automatic change on adoption is the
helper `install` path migrating an older config's transport to socket/pipe
via the single writer. Rollback: stop the service, reinstall the previous
binaries (or copy `<binary>.old` back), restore the backed-up config bytes
named by the operation, restart, and verify `ExecStart`/`sc qc` binPath,
control-plane reachability, and `skein status`.

## Known residuals (not closed by this ADR)

- Daemon-side environment variables `SKEIN_NO_FIREWALL` and
  `SKEIN_STATE_FILE` are honoured in release builds (operator variables,
  not dev-gated like the GUI/CLI security variables). Follow-up: give them
  the same release/dev treatment, or bless them explicitly as operator
  variables — do not silently leave a firewall-disable switch env-gated.
  See README Environment and `docs/engineering/M9-ACCEPTANCE.md`.
- Portable/zip layouts on Windows (helper or `wintun.dll` beside an
  executable in a user-writable directory) are not blessed installs; the
  packaged NSIS layout (admin-only install directory) is the safe one.
- Release artefacts are unsigned in-repo, and the GUI has no automatic
  update check by design (operator-driven About/Updates flow only).

## Enforcement

`scripts/collapse-gates.sh` (single writer, no daemon spawn from GUI/CLI,
no removed helper verb called from GUI/CLI, no direct service registration,
no bootstrap route in the normal handler, allow-listed writers, no secret
logging, no reappeared Step 12 deletion) and
`scripts/packaging-assert.sh` (installer manifests ship daemon + minimal
helper + CLI + Wintun on Windows; daemon + helper + CLI + unit + group +
polkit on Linux; uninstall order; purge behaviour) both run in CI and must
stay green. Weakening a gate to make a change pass is forbidden.
